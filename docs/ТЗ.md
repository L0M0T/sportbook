# Техническое задание

**Проект:** SportBook — система онлайн-записи в спортивный центр
**Версия:** 1.0 · **Дата:** 09.11.2026
**Заказчик:** учебный проект (вымышленный спортцентр, один зал)
**Исполнитель:** 1 разработчик · **Срок:** 10 рабочих дней
**Статус:** на согласовании

Приоритеты по MoSCoW: **Must** — без этого проект не сдан, **Should** — делаем, если успеваем, **Could** — задел на будущее.

---

## 1. Общие сведения

Система позволяет клиенту спортцентра записаться на групповую или персональную тренировку, оплатить абонемент, отменить или перенести запись, пройти чек-ин по QR-коду. Администратор управляет расписанием, пользователями и абонементами, смотрит отчёты. Менеджер (ресепшн) работает с записями и чек-ином, но не удаляет пользователей и не меняет настройки.

**Цель документа:** превратить 12 требований преподавателя из пожеланий в проверяемые критерии (раздел 2) и зафиксировать объём MVP.

## 3. Границы проекта и допущения

| Решение | Почему |
|---|---|
| Мобильное — **PWA**, не нативное приложение | Один код на веб и телефон; нативная сборка не влезает в 10 дней одному |
| SMS и оплата — **адаптеры с mock-реализацией** | Нет бюджета и юрлица; реальный провайдер подключается заменой одного класса, без переписывания логики |
| Офлайн — **только просмотр расписания** | Запись офлайн создаёт конфликты мест; полноценная синхронизация — отдельный проект |
| «Резерв» = бэкап + автоперезапуск + восстановление ≤ 1 ч | Второй сервер (active-passive) не оправдан для одного зала и учебного бюджета |
| 152-ФЗ формально не применяется (центр вымышленный) | Но согласие на обработку ПД, минимизация и базовая защита заложены |
| Один зал, часовой пояс Europe/Moscow | Упрощает расписание и отчёты |

**Вне объёма MVP:** лист ожидания, email-рассылки, нативные приложения, реальный эквайринг, второй сервер, программа лояльности.

## 8. Ключевые сценарии

**Запись на групповую тренировку**
1. Клиент открывает расписание и выбирает тренировку.
2. Видит свободные места, тренера, зал, цену.
3. Нажимает «Записаться» → система в транзакции проверяет место и баланс абонемента.
4. Создаётся бронь и QR, приходит подтверждение.
5. Если мест нет — понятное сообщение, запись не создаётся.

**Перенос записи**
1. Клиент открывает «Мои записи» → «Перенести».
2. Выбирает новый слот из доступных.
3. Если до старта ≥ 2 ч — занятие не списывается повторно; иначе перенос запрещён.
4. Старая бронь отменяется, новая создаётся атомарно.

**Чек-ин**
1. Клиент показывает QR на ресепшн.
2. Менеджер сканирует → проверяются подпись, окно действия, статус брони.
3. Первый успешный скан списывает занятие и ставит `checkedInAt`; повторный — идемпотентен.

**Отмена тренировки админом**
1. Админ отменяет тренировку с причиной.
2. Все активные брони переводятся в «отменено», занятия возвращаются.
3. Каждому записанному уходит in-app + push + SMS (по настройке), доставка логируется.

## 9. Архитектура и стек

- **Next.js 15 (App Router) + TypeScript strict** — фронт и бэк в одном проекте.
- **Prisma + PostgreSQL** (SQLite для локальной разработки).
- **Tailwind CSS + shadcn/ui** — тёмная тема, дизайн-токены.
- **Auth:** собственная OTP-аутентификация по телефону, сессия в httpOnly-cookie.
- **Валидация:** Zod на всех входах.
- **Провайдеры через интерфейсы:** `SmsProvider`, `PaymentProvider`, `PushProvider` → mock-реализации; реальные подключаются конфигом.
- **Тесты:** Vitest (логика), Playwright (smoke: вход → запись → отмена).
- **PWA:** manifest + service worker, кэш расписания.
- **Деплой:** Vercel + Neon Postgres (или Docker Compose локально).

Структура: `app/` (страницы и API), `components/`, `lib/` (домен, провайдеры), `prisma/`, `tests/`.

## 13. Приёмка (демо-сценарий, 7 минут)

1. Вход клиентом по коду, запись на групповую тренировку — 1 мин.
2. Попытка записаться на заполненную тренировку — показ ошибки — 30 с.
